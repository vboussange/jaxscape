# Tiles for sources that share work

Windowed analyses compute a block centre's distances on the graph of its window, or of a tile: the union of the windows of a grid of block centres, whose distances one query computes. A distance declares with the class attribute `sources_share_work` whether a query from several sources costs much less than one query per source; the analyses read it and never check distance types. Resistance sets it: a query factorizes the tile's Laplacian once and solves for every pixel of the tile whatever the number of sources, and a Spielman query embeds every pixel with the same solves. LCP and Euclidean distances keep one window per block centre, batched with `vmap`: on a shared tile, LCP would do about 8 times more work per source. `batch_size` is the number of block centres processed together in both cases, and `batch_size=1` gives every distance its own window. A tile graph extends beyond each window, so its distances are lower: about 3 % more connectivity at `dependency_range` 20.

Spec #36 measured the alternatives. Batching windows into a block-diagonal system gains nothing for sparse solvers, which a single window already saturates, and multiplies memory. A tile path specific to Spielman embeddings, with neighbourhood sums from Gram blocks of the embedding, avoids holding the distances from every source to every tile pixel, but needs the engine to know the distance; the analyses instead call the distance's ordinary query, and `batch_size` bounds that memory. Randomized distances correct the proximity of their estimates through `AbstractDistance.debiased_proximity`, and the default proximity is read off the distance that they estimate, `AbstractDistance.exact`, so that the engine stays agnostic there too: one randomized profile biased Spielman connectivity by +16 % at `epsilon` 0.1 and +37 % at 0.2.
